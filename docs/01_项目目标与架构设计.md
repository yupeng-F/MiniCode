# 项目目标与架构设计

## 1. 项目定位

本项目定位为：

```text
Local-first Agentic Coding Assistant
本地优先、以 Tool-Use Loop 为核心、由 Harness Runtime 约束的编码 Agent
```

它不是一个单纯的多 Agent 流程 Demo，而是一个面向真实本地仓库的 coding assistant。

最终能力目标：

- 理解本地代码仓库
- 搜索、阅读、修改代码
- 生成并执行补丁
- 运行测试与静态检查
- 审查改动风险
- 在副作用动作前进行策略判断与人工审批
- 沉淀项目规则、用户偏好和失败案例
- 通过 CLI 与 Web UI 提供透明、可控的交互体验

### 当前落地状态（2026-07-17）

架构迁移已经完成：旧 `multi_agents / LangGraph` 固定状态机已删除，`src/minicode/` 成为唯一运行主线。

- 模型驱动的 `QueryLoop`，支持结构化 DeepSeek 工具历史、循环恢复与完成熔断

- 工作区内的 Read / Glob / Grep / Patch / Test / Git / Bash 工具
- 文件分页读取、工具结果预算、消息压缩、ArtifactStore 和敏感信息过滤
- 项目隔离的 Markdown Memory 基线与验证后自动写入规则
- SQLite 项目/会话索引、独立 run 生命周期、审批 API 与会话隔离
- React + TypeScript + Vite 三栏工作台，支持项目/会话管理、文件查看和审批

迁移后仍待产品化完善：

- 受控 `task_agent` SubAgent

- 完整 Diff / Plan / Artifact / Memory 管理界面和 SSE 状态流

因此本文后续章节同时包含“已实现架构”和“目标扩展设计”；实施进度以唯一产品化计划顶部状态表为准。

## 2. 设计参考

本阶段架构设计参考了 Claude Code 的拆解思路，重点吸收以下思想：

- 核心是模型驱动的 `Tool-Use Loop`，而不是固定的多 Agent 工作流
- 工具需要声明安全属性，如只读、副作用、破坏性、是否可并发
- Harness Runtime 是工程核心，负责工具执行、安全策略、审批和审计
- 代码检索优先使用 `Glob / Grep / Read`，不把 RAG 作为源码理解主路径
- 上下文需要分层裁剪、压缩和 artifact 化，不能把所有工具输出塞进 prompt
- 记忆优先使用 Markdown 文件，向量库作为可选辅助
- SubAgent 应作为 `Task tool` 按需启动，而不是固定流程节点

## 4. 运行核心：Tool-Use Loop

主架构采用 `Tool-Use Loop`：

```python
while True:
    context = context_manager.build(session)
    response = model.call(context, tools=tool_registry.visible_tools(session))

    if response.type == "final":
        return response

    if response.type == "tool_use":
        result = runtime.execute(response.tool_call)
        session.append_tool_result(result)
        continue
```

会话生命周期、审批暂停与恢复由 `QueryLoop + SQLite + Approval API` 实现，不依赖图编排框架。

## 5. 工具系统设计

工具是 Agent 的能力边界，也是安全治理的入口。

建议的工具声明：

```python
class ToolSpec:
    name: str
    description: str
    input_schema: dict

    read_only: bool
    side_effect: bool
    destructive: bool
    supports_parallel: bool
    requires_approval: bool

    allowed_modes: list[str]
    allowed_roles: list[str]

    risk: RiskProfile
```

风险模型：

```python
class RiskProfile:
    reversibility: Literal["reversible", "hard_to_reverse", "irreversible"]
    blast_radius: Literal["none", "file", "workspace", "system", "network"]
    data_exposure: Literal["none", "local_only", "external"]
    approval: Literal["never", "on_policy", "always"]
```

第一批核心工具：

```text
read_file
list_directory
glob_files
grep
edit_file
propose_patch
apply_patch
run_tests
git_status
git_diff
bash
task_agent
enter_plan_mode
exit_plan_mode
```

工具使用原则：

- 搜索代码优先使用 `grep`
- 找文件优先使用 `glob_files`
- 读文件必须使用 `read_file`
- 修改文件优先使用 `edit_file` / `propose_patch` / `apply_patch`
- 运行测试优先使用 `run_tests`
- `bash` 只作为兜底工具，并默认进入更严格的策略检查

## 6. 代码检索方案

源码理解主路径采用：

```text
Glob -> Grep -> Read
```

不把向量检索作为源码理解默认路径。

原因：

- 冷启动快，不需要先构建索引
- 实时性好，文件改动后立即可见
- 精确性好，函数名、变量名和路径匹配更可靠
- 可解释性好，每次检索结果都能展示给用户
- token 成本更可控

技术方案：

- 底层优先使用 `ripgrep`
- Python 侧包装为结构化工具结果
- `read_file` 支持 offset / limit
- grep 结果包含 path、line、preview、match_count
- 大结果进入 ArtifactStore，prompt 只保留 preview

向量库只用于辅助：

- 历史任务经验
- 用户偏好
- 失败案例
- 外部文档摘要

## 7. 上下文管理方案

ContextManager 的职责不是保存一切，而是在每次模型调用前投影当前最重要的信息。

上下文分层：

```text
System Prompt
Project Rules
Memory Index
Active Task
Recent Messages
Tool Results
Active Files
Plan
```

压缩策略：

```text
Level 0: 工具结果 preview，完整内容进 artifact
Level 1: read_file 默认 offset / limit
Level 2: grep / glob 设置结果上限
Level 3: 旧 tool_result 替换成摘要
Level 4: 对话历史 micro compact
Level 5: Auto compact，把旧上下文压成任务摘要
```

建议运行目录：

```text
.minicode/
  runs/
    {run_id}/
      artifacts/
      trace.jsonl
      state.json
      compact.md
```

## 8. 记忆系统设计

长期记忆以 Markdown 文件为主，ChromaDB 作为可选辅助。

建议目录：

```text
.minicode/
  memory/
    MEMORY.md
    project/
    user/
    failures/
    rules/
```

记忆分层：

- `Managed`：系统级固定规则
- `User`：用户全局偏好
- `Project`：项目规则，可签入 git
- `Local`：本地私有规则，不签入 git
- `Auto`：Agent 自动学习的经验
- `Team`：后续可扩展的团队共享记忆

`MEMORY.md` 作为索引常驻上下文，详细记忆按需加载。

条件规则示例：

```markdown
---
name: frontend-rule
paths: ["**/*.tsx", "**/*.jsx"]
---

编辑 React 文件时遵守这些规范。
```

只有当当前任务涉及匹配路径时，规则才进入上下文。

## 9. 多 Agent 方案

固定的 Explorer / Coder / Reviewer / Tester 后续逐步弱化，改为：

```text
主 Agent + task_agent 工具启动 SubAgent
```

示例：

```text
task_agent(
  role="explorer",
  task="调查认证模块结构",
  allowed_tools=["grep", "glob_files", "read_file"],
  budget=10
)
```

内置 SubAgent 模板：

- `explorer`：开放式代码探索，只读
- `reviewer`：审查当前 diff，只读
- `tester`：运行测试，可执行测试命令
- `researcher`：查文档，后续可联网

隔离要求：

- 工具隔离
- 上下文隔离
- 状态隔离
- 只返回 summary、findings 和 artifact_refs

## 10. 安全治理方案

安全原则：

```text
默认只读
工作区内执行
副作用可审计
高风险需审批
专用工具优先
Bash 最小化
```

核心模块：

```text
WorkspaceManager
  resolve_path
  ensure_inside_workspace
  deny_symlink_escape
  deny_hidden_sensitive_files

PolicyEngine
  evaluate_tool_spec
  evaluate_path
  evaluate_command
  evaluate_mode

ApprovalGate
  diff approval
  command approval
  plan exit approval

AuditLogger
  edit_file / apply_patch
  bash
  git operation
  approval decision
```

策略示例：

- `read_file / grep / glob_files` 自动允许
- `edit_file` 生成 diff，可配置小范围自动允许
- `apply_patch` 默认审批
- `run_tests` 自动允许
- `bash` 默认审批
- `git push / rm / sudo / curl / chmod` 强审批或禁止

## 11. Plan Mode 设计

Plan Mode 作为工具能力实现，而不是独立流程分支。

工具：

```text
enter_plan_mode
exit_plan_mode
```

进入 Plan Mode：

- session.mode = plan
- 只允许只读工具
- 禁止 edit_file / apply_patch / bash / git write

退出 Plan Mode：

- 输出计划
- 用户审批
- 审批通过后切回 act

计划落盘：

```text
.minicode/plans/{run_id}.md
```

## 12. 运行形态

最终运行方式：

```text
Local daemon + Web UI + CLI
```

也就是：

- 用户本机启动 FastAPI local daemon
- Web UI 连接本地服务
- CLI 也连接同一个本地服务
- 所有文件操作都在用户指定 workspace 内
- 默认不把代码上传到自有服务器

示例命令：

```bash
minicode serve --workspace /path/to/repo
minicode chat
minicode run "帮我修复测试失败"
```

短期不优先做 Electron / Tauri，先做好：

```text
FastAPI local daemon + 原生 Web UI + CLI
```

## 13. 交互方式

CLI：

- 适合真实开发
- 适合快速执行任务
- 适合展示核心能力

Web UI：

- 适合可视化展示
- 适合审批 diff
- 适合查看 trace / memory / tool results
- 适合作为作品展示

Web UI 推荐布局：

```text
左侧：文件树 / 修改文件 / 运行历史
中间：对话 / 当前计划
右侧：Trace / State / Memory / Agent
底部：Tool output / Diff / Approval / Test result
```

## 14. 数据持久化方案

采用：

```text
SQLite + 文件系统
```

SQLite 存结构化索引：

- runs
- sessions
- messages
- tool_calls
- approvals
- artifacts
- memories

文件系统存大内容：

```text
.minicode/
  runs/
  artifacts/
  memory/
  plans/
  audit/
```

SQLite 适合本地工具，部署成本低，查询和恢复能力比纯 JSON 更好。
