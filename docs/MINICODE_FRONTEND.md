# MiniCode 前端规范

## 1. 技术基线

- 前端位于 `web/`，使用 React 函数组件、TypeScript strict 模式与 Vite。
- 组件以明确的 props 和状态边界组织，不引入与当前任务无关的全局状态框架。
- 新增界面保持现有 MiniCode 三栏工作台的视觉语言、间距、颜色和交互层级。
- Harness 接入不强制使用 Vue、Pinia 或 Tailwind，也不以迁移框架作为功能开发的前置条件。

## 2. API Client

- 所有 HTTP 请求集中在 `web/src/api.ts`；组件与 Hook 不直接调用 `fetch`。
- API Client 负责 URL、请求体、响应解析和非成功状态的统一错误转换。
- 请求与响应类型必须显式声明，并与后端 Pydantic Schema 的字段语义一致。
- 新端点先扩展 API Client 及其 Vitest 测试，再由组件调用。

## 3. 会话状态与轮询

- 运行中的 session 可以轮询状态，但每个视图只保留一个有效轮询链。
- `useEffect` 必须返回清理函数，组件卸载、session/run 切换和终态到达时取消 timer；过期响应不得覆盖当前选择。
- `completed`、`failed`、`cancelled` 与审批拒绝等终态停止轮询。
- 创建 run、提交审批和刷新 session 的并发操作必须禁用重复提交或识别过期响应。

## 4. 必备界面状态

每个异步区域必须显式呈现：

- 加载状态：告知用户正在读取或运行，避免无反馈空白。
- 空状态：说明当前没有项目、会话、工具结果或审批，并提供可执行的下一步。
- 错误状态：展示可理解且可重试的消息，不显示堆栈或敏感路径。
- 审批状态：明确展示工具、影响范围、diff 或命令，以及批准和拒绝操作。
- 结果状态：区分工具调用中、成功、失败、等待审批，并保留摘要与 Artifact 引用。

## 5. 可访问性

- 所有主要流程支持键盘操作；按钮、链接和表单控件不得只依赖鼠标或 hover。
- 交互控件必须有可见焦点，不能用样式移除焦点反馈而不提供等价替代。
- 使用语义化的 `button`、`label`、标题、列表和状态区域；图标按钮提供可读名称。
- 加载、错误和审批变化通过合适的语义标签或 live region 传达，颜色不是唯一状态线索。
- 对话框或审批面板打开后管理焦点，关闭后把焦点还给触发控件。

## 6. 测试与完成定义

- Vitest 覆盖 API Client 的成功与错误解析，以及组件或状态逻辑的加载、空、错误、轮询清理和审批分支。
- 测试替换网络边界，不访问真实后端或外部服务；定时器测试必须证明 cleanup 后不再请求。
- 类型检查必须覆盖 strict 模式，Lint 不得留下错误，Vite 生产构建必须成功。

前端变更完成必须满足相关 Vitest 先红后绿，并从仓库根目录通过：

```bash
pnpm typecheck && pnpm lint && pnpm test && pnpm build
```
