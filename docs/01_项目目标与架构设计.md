# 项目目标与架构设计

## 1. 项目定位

本项目定位为：

```text
Local-first Agentic Coding Assistant
本地优先、以 Tool-Use Loop 为核心、由 Harness Runtime 约束的编码 Agent
```

它不是一个单纯的多 Agent 流程 Demo，而是一个面向真实本地仓库的 coding assistant。

最终能力目标：

- 理解本地代码仓库
- 搜索、阅读、修改代码
- 生成并执行补丁
- 运行测试与静态检查
- 审查改动风险
- 在副作用动作前进行策略判断与人工审批
- 沉淀项目规则、用户偏好和失败案例
- 通过 CLI 与 Web UI 提供透明、可控的交互体验

### 当前落地状态（2026-08-20）

架构迁移已经完成：旧 `multi_agents / LangGraph` 固定状态机已删除，`src/minicode/` 成为唯一运行主线。

已经落地：

- 模型驱动的 `QueryLoop`，支持结构化 DeepSeek 工具历史、循环恢复与完成熔断
- `HarnessRuntime + ToolSpec + RiskProfile + PolicyEngine + ApprovalGate`
- 工作区内的 Read / Glob / Grep / Patch / Test / Git / Bash 工具
- 文件分页读取、工具结果预算、消息压缩、ArtifactStore 和敏感信息过滤
- 项目隔离的 Markdown Memory 基线与验证后自动写入规则
- SQLite 项目/会话索引、独立 run 生命周期、审批 API 与会话隔离
- React + TypeScript + Vite 三栏工作台，支持项目/会话管理、文件查看和审批
- SQLite Run checkpoint 与有序 Event 流，支持 daemon 重启恢复、SSE 回放和原子审批 claim
- 只读受控 `task_agent`，提供独立且有预算限制的 explorer / reviewer
- append-only Trace/Audit、审计前敏感信息清理与可重复 JSON Eval CLI
- Markdown Memory 候选、去重、晋升、冲突替换、禁用/删除治理及 Web 查看界面

迁移后仍待产品化完善：

- Run cancel、会话 rename/archive 和更细的崩溃恢复用户引导
- 完整 Artifact 预览/下载、可视化 Audit/Eval 报告和响应式抽屉
- 更丰富的前端组件测试与发布级回归场景
- 写入型 SubAgent（若开放）的显式审批与更严格隔离
- 长、中、短三级记忆、SQLite FTS5 + ChromaDB 混合检索与历史记忆治理
- `TokenBudget` 全链路接入、48,000 token 输入硬上限和 Prompt 分区预算
- Flash / Pro 会话级选择、Run 级模型固化和 Embedding 状态可观测性

因此本文后续章节同时包含“已实现架构”和“目标扩展设计”；实施进度以唯一产品化计划顶部状态表为准。

## 2. 设计参考

本阶段架构设计参考了 Claude Code 的拆解思路，重点吸收以下思想：

- 核心是模型驱动的 `Tool-Use Loop`，而不是固定的多 Agent 工作流
- 工具需要声明安全属性，如只读、副作用、破坏性、是否可并发
- Harness Runtime 是工程核心，负责工具执行、安全策略、审批和审计
- 代码检索优先使用 `Glob / Grep / Read`，不把 RAG 作为源码理解主路径
- 上下文需要分层裁剪、压缩和 artifact 化，不能把所有工具输出塞进 prompt
- 记忆优先使用 Markdown 文件，向量库作为可选辅助
- SubAgent 应作为 `Task tool` 按需启动，而不是固定流程节点

## 4. 运行核心：Tool-Use Loop

主架构采用 `Tool-Use Loop`：

```python
while True:
    context = context_manager.build(session)
    response = model.call(context, tools=tool_registry.visible_tools(session))

    if response.type == "final":
        return response

    if response.type == "tool_use":
        result = runtime.execute(response.tool_call)
        session.append_tool_result(result)
        continue
```

会话生命周期、审批暂停与恢复由 `QueryLoop + SQLite + Approval API` 实现，不依赖图编排框架。

## 5. 工具系统设计

工具是 Agent 的能力边界，也是安全治理的入口。

建议的工具声明：

```python
class ToolSpec:
    name: str
    description: str
    input_schema: dict

    read_only: bool
    side_effect: bool
    destructive: bool
    supports_parallel: bool
    requires_approval: bool

    allowed_modes: list[str]
    allowed_roles: list[str]

    risk: RiskProfile
```

风险模型：

```python
class RiskProfile:
    reversibility: Literal["reversible", "hard_to_reverse", "irreversible"]
    blast_radius: Literal["none", "file", "workspace", "system", "network"]
    data_exposure: Literal["none", "local_only", "external"]
    approval: Literal["never", "on_policy", "always"]
```

第一批核心工具：

```text
read_file
list_directory
glob_files
grep
edit_file
propose_patch
apply_patch
run_tests
git_status
git_diff
bash
task_agent
enter_plan_mode
exit_plan_mode
```

工具使用原则：

- 搜索代码优先使用 `grep`
- 找文件优先使用 `glob_files`
- 读文件必须使用 `read_file`
- 修改文件优先使用 `edit_file` / `propose_patch` / `apply_patch`
- 运行测试优先使用 `run_tests`
- `bash` 只作为兜底工具，并默认进入更严格的策略检查

## 6. 代码检索方案

源码理解主路径采用：

```text
Glob -> Grep -> Read
```

不把向量检索作为源码理解默认路径。

原因：

- 冷启动快，不需要先构建索引
- 实时性好，文件改动后立即可见
- 精确性好，函数名、变量名和路径匹配更可靠
- 可解释性好，每次检索结果都能展示给用户
- token 成本更可控

技术方案：

- 底层优先使用 `ripgrep`
- Python 侧包装为结构化工具结果
- `read_file` 支持 offset / limit
- grep 结果包含 path、line、preview、match_count
- 大结果进入 ArtifactStore，prompt 只保留 preview

向量库只用于辅助：

- 历史任务经验
- 用户偏好
- 失败案例
- 外部文档摘要

## 7. 上下文管理方案

ContextManager 的职责不是保存一切，而是在每次模型调用前投影当前最重要的信息。

每次模型调用采用统一硬限制：

```text
最大输入 Prompt：48,000 tokens
最大模型输出：8,000 tokens
安全预留：8,000 tokens
最低模型上下文要求：64,000 tokens
```

即使模型支持更大上下文，MiniCode 默认也不把 Prompt 扩大到模型极限。现有
`TokenBudget` 必须接入 `ContextManager`、原生工具历史和 Provider 发送前校验，
不能只限制一个局部字符串。

### 7.1 Token 计算

Token 计算采用：

```text
TokenCounter
├── TiktokenCounter
├── MixedLanguageEstimator
└── SafeTokenCounter
```

最终估算值取 tiktoken 与中英文混合启发式结果的较大值，并乘以 `1.10` 安全
系数。不能继续使用单一的 `len(text) // 4`，因为它会严重低估中文内容。

### 7.2 Prompt 分区预算

```text
System Prompt + Tool Specs       8,000
当前任务/最新用户消息             12,000
最近对话                         8,000
工具调用历史与结果               10,000
混合检索记忆                     4,000
Compact Summary                 3,000
Plan / Active Files / Metadata  2,000
安全余量                         1,000
────────────────────────────────────
总输入上限                       48,000
```

分区是软配额，总上限是硬限制。未使用额度可以在分区间借用，但最新用户消息
仍不得超过 `12,000 tokens`。最新任务只在 `Current Task` 出现一次，不再同时
重复写入 `Recent Messages`。

### 7.3 超限处理

每次调用模型前按顺序执行：

```text
1. 工具完整结果进入 Artifact，只保留 preview
2. 删除最旧、最低价值的工具 preview
3. 删除最低相关度记忆
4. 压缩较旧对话
5. 缩减中期历史摘要
6. 重新计算完整请求 token
7. 仍超限则停止 Run，并返回明确错误
```

不得静默截断最新用户消息。单条消息超过 `12,000 tokens` 时，前端阻止发送，
后端再次校验并返回 `422`，提示用户将长内容保存为工作区文件后使用
`read_file` 分页读取。

ContextManager 输出结构化投影：

```text
ContextProjection
├── prompt
├── tool_history
├── memory_refs
├── estimated_input_tokens
├── section_usage
├── truncated_sections
└── budget_limit
```

预算范围必须包含 System Prompt、工具 schema、原生 assistant/tool 历史、
`reasoning_content`、JSON 参数和工具结果。Provider 在真正发送请求前执行第二次
硬上限校验。

每次模型调用记录模型、估算输入 token、输出上限、各分区用量、压缩动作和预算
上限；不记录被过滤掉的敏感正文。

## 8. 记忆系统设计

记忆系统采用短期、中期、长期三层模型。Markdown 是长期记忆正文的唯一事实
来源，SQLite FTS5 负责关键词检索，ChromaDB 仅保存可重建的向量索引。

总体组件：

```text
MemoryManager
├── ShortTermMemory
├── MediumTermMemory
├── LongTermMemory
├── MemoryIndex
├── EmbeddingProvider
└── HybridRetriever
```

### 8.1 记忆层级

短期记忆：

- 当前任务、最近消息、工具结果、计划和活动文件
- 存在 SessionState 与 Run checkpoint 中
- 不进入向量库
- 每轮由 TokenBudget 重新投影和裁剪

中期记忆：

- 每次完成 Run 后生成结构化摘要
- 保存任务、结果、状态、涉及文件、失败原因和时间
- 只允许当前项目检索
- 默认保留 30 天，每个项目最多 200 条
- 按时间衰减、检索相关度和使用次数淘汰
- 用户固定后不自动淘汰，并可晋升为长期记忆

长期记忆：

- 项目规则、确认后的用户偏好、验证成功的命令和失败经验
- 项目记忆位于 `.minicode/memory/`
- 全局用户偏好位于 `~/.minicode/memory/user/`
- 普通项目历史禁止跨项目检索
- 自动捕获只创建 candidate，不直接启用

项目目录：

```text
.minicode/
  memory/
    MEMORY.md
    rules/
    preferences/
    failures/
    candidates/
    memory.db
    chroma/
```

统一记录字段：

```text
MemoryRecord
├── id
├── project_id
├── scope              project | global_user
├── tier               medium | long
├── kind               rule | preference | episode | failure | command | summary
├── status             candidate | enabled | disabled
├── title
├── content
├── paths[]
├── source
├── pinned
├── importance
├── created_at / updated_at / expires_at
├── last_accessed_at / access_count
├── content_hash
└── metadata
```

中期记忆正文和统计信息存项目 SQLite；长期正文存 Markdown，SQLite 只保存检索
索引与元数据；ChromaDB 只保存 `memory_id`、向量、作用域和内容哈希。

### 8.2 task 驱动的混合检索

检索接口调整为：

```python
MemoryService.retrieve(
    task: str,
    active_files: list[str],
    mode: str,
    max_tokens: int = 4_000,
) -> MemoryRetrievalResult
```

`task` 必须真实参与查询。检索文本由当前 task、活动文件路径和 mode 构成，
`MemoryRetrievalResult` 返回候选、分项得分、引用、Provider 和降级信息。检索同时执行：

1. SQLite FTS5 关键词/BM25 检索
2. Embedding 向量相似度检索
3. 项目、状态、路径和有效期过滤

关键词归一化保留英文与代码标识符、拆分文件路径，并为中文生成二元和三元词片段，
避免依赖空格分词或额外引入 jieba。

每路取前 30 条候选，排名归一化后融合：

```text
final_score =
    0.45 × vector_rank
  + 0.30 × keyword_rank
  + 0.10 × path_match
  + 0.10 × recency
  + 0.05 × usefulness
```

中期记忆按 30 天指数衰减，长期规则不衰减。候选、禁用和过期内容在评分前排除。
最终最多注入 8 条、总计 4,000 tokens、单条不超过 1,000 tokens，并将引用写入
`session.memory_refs`。

### 8.3 Embedding Provider

远程主 Provider：

```text
provider: Alibaba Cloud Model Studio
model: qwen3.7-text-embedding
dimensions: 1024
key: DASHSCOPE_API_KEY
workspace: DASHSCOPE_WORKSPACE_ID
region: DASHSCOPE_REGION=cn-beijing
```

有 Workspace ID 时，后端生成：

```text
https://{WorkspaceId}.cn-beijing.maas.aliyuncs.com/compatible-mode/v1
```

否则使用仍兼容的公共地址：

```text
https://dashscope.aliyuncs.com/compatible-mode/v1
```

完整 URL 可通过 `DASHSCOPE_BASE_URL` 覆盖。Key 只从 `.env` 或进程环境读取，
不进入数据库、Markdown、Trace、Audit、错误正文或前端 API。

本地兜底 Provider：

```text
runtime: FastEmbed / ONNX
model: BAAI/bge-small-zh-v1.5
dimensions: 512
download size: about 90 MB
```

本地模型不在普通 Run 中静默下载，通过
`minicode memory setup-local-embedding` 或 Web 显式按钮初始化。阿里云与本地
模型使用不同 Chroma collection，禁止混写不同维度向量。

远程调用发生时，Web UI 显示 Provider、模型、外部传输、耗时和降级状态；不显示
正文或 Key。敏感信息过滤器发现 Key、Token 或密码时，该内容禁止发送到远程
Embedding，只允许本地或 FTS5 检索。

### 8.4 降级与索引一致性

前台远程 Embedding 超时上限为 8 秒，不自动重试；失败后依次降级为本地模型和
FTS5。Embedding 故障不能使 Agent 主任务失败。后台索引任务最多重试 3 次并采用
指数退避；鉴权错误不重试。

写入顺序：

```text
写入 Markdown/SQLite 正文
→ 同步更新 FTS5
→ 创建 embedding_index_job
→ 异步更新 ChromaDB
```

索引使用 `content_hash` 校验。正文变化、禁用、删除或模型切换时更新相应向量；
服务启动扫描 pending、error 和 hash mismatch。ChromaDB 损坏时从 Markdown 与
SQLite 全量重建，不影响正文。

首次迁移保留现有 Memory ID、状态、来源和路径，已禁用内容保持禁用，不删除或
改写现有 Markdown 正文。旧 Session 缺少模型字段时使用默认 Flash。

### 8.5 Memory 可观测性

UI 记忆详情展示层级、作用域、关键词/向量/路径/时间得分、Provider、外部传输、
索引状态和降级原因。每次 Run 完成后生成中期摘要、同步 FTS5 并异步更新向量索引。

### 8.6 模型选择与消息发送

对话模型采用会话级默认、Run 级固化：

- 新会话默认 `deepseek-v4-flash`
- 用户可切换 `deepseek-v4-pro`
- Run 创建时把模型 ID 写入 checkpoint
- Run 期间禁止切换，结束、失败或取消后允许切换
- 审批恢复和 daemon 重启继续使用原 Run 模型
- SubAgent 默认继承父 Run 模型
- 后端只接受模型白名单，不接受前端任意模型名称

模型目录结构：

```text
ModelProfile
├── id
├── display_name
├── provider
├── context_window
├── max_input_tokens
├── max_output_tokens
├── supports_tools
└── is_default
```

初始配置：

```env
MINICODE_DEFAULT_MODEL=deepseek-v4-flash
MINICODE_ALLOWED_MODELS=deepseek-v4-flash,deepseek-v4-pro
```

`GET /api/capabilities` 返回允许的对话模型、默认模型、Embedding Provider/模型/
外部传输/兜底状态和 Token 上限，但不返回任何 Key。Session 与 Run API 接收并
校验 `model_id`；未知或未启用模型返回 `400`。

Web Composer 使用 `Enter` 发送、`Shift+Enter` 换行；输入法组合期间 Enter 不
发送。空消息和 Run 期间禁止发送。

## 9. 多 Agent 方案

固定的 Explorer / Coder / Reviewer / Tester 后续逐步弱化，改为：

```text
主 Agent + task_agent 工具启动 SubAgent
```

示例：

```text
task_agent(
  role="explorer",
  task="调查认证模块结构",
  allowed_tools=["grep", "glob_files", "read_file"],
  budget=10
)
```

内置 SubAgent 模板：

- `explorer`：开放式代码探索，只读
- `reviewer`：审查当前 diff，只读
- `tester`：运行测试，可执行测试命令
- `researcher`：查文档，后续可联网

隔离要求：

- 工具隔离
- 上下文隔离
- 状态隔离
- 只返回 summary、findings 和 artifact_refs

## 10. 安全治理方案

安全原则：

```text
默认只读
工作区内执行
副作用可审计
高风险需审批
专用工具优先
Bash 最小化
```

核心模块：

```text
WorkspaceManager
  resolve_path
  ensure_inside_workspace
  deny_symlink_escape
  deny_hidden_sensitive_files

PolicyEngine
  evaluate_tool_spec
  evaluate_path
  evaluate_command
  evaluate_mode

ApprovalGate
  diff approval
  command approval
  plan exit approval

AuditLogger
  edit_file / apply_patch
  bash
  git operation
  approval decision
```

策略示例：

- `read_file / grep / glob_files` 自动允许
- `edit_file` 生成 diff，可配置小范围自动允许
- `apply_patch` 默认审批
- `run_tests` 自动允许
- `bash` 默认审批
- `git push / rm / sudo / curl / chmod` 强审批或禁止

## 11. Plan Mode 设计

Plan Mode 作为工具能力实现，而不是独立流程分支。

工具：

```text
enter_plan_mode
exit_plan_mode
```

进入 Plan Mode：

- session.mode = plan
- 只允许只读工具
- 禁止 edit_file / apply_patch / bash / git write

退出 Plan Mode：

- 输出计划
- 用户审批
- 审批通过后切回 act

计划落盘：

```text
.minicode/plans/{run_id}.md
```

## 12. 运行形态

最终运行方式：

```text
Local daemon + Web UI + CLI
```

也就是：

- 用户本机启动 FastAPI local daemon
- Web UI 连接本地服务
- CLI 也连接同一个本地服务
- 所有文件操作都在用户指定 workspace 内
- 默认不把代码上传到自有服务器

示例命令：

```bash
minicode serve --workspace /path/to/repo
minicode chat
minicode run "帮我修复测试失败"
```

短期不优先做 Electron / Tauri，先做好：


## 14. 数据持久化方案

采用：

```text
SQLite + 文件系统
```

SQLite 存结构化索引：

- runs
- sessions
- messages
- tool_calls
- approvals
- artifacts
- memories

文件系统存大内容：

```text
.minicode/
  runs/
  artifacts/
  memory/
  plans/
  audit/
```

SQLite 适合本地工具，部署成本低，查询和恢复能力比纯 JSON 更好。

## 18. Memory / Context / Model 扩展验收标准

后端自动化测试必须覆盖：

- task 变化会改变检索结果，中文词片、代码标识符和路径均可召回
- 项目历史隔离，全局用户偏好可跨项目召回
- RRF 排名、路径加权、30 天/200 条淘汰和 pinned 保护
- 内容哈希变化触发索引重建，禁用/删除内容不再召回
- 阿里云失败后依次降级本地与 FTS5，Embedding 故障不阻塞主任务
- 敏感内容禁止远程向量化
- 中英文 Token 估算不超过安全误差，单条超限返回 `422`
- 完整 Prompt（含 tool schema/history/reasoning）不超过 48,000 tokens
- Run 固化模型，结束后允许切换，审批恢复使用原模型

前端组件测试必须覆盖：

- Enter 发送、Shift+Enter 换行、中文输入法 Enter 不误发送
- Run 中模型选择禁用，Run 结束后恢复
- Flash 默认、Pro 可选
- 远程外传、本地降级和纯关键词检索状态可见
- Token 使用量、压缩动作和超限错误可见

浏览器真实验收至少包括：

1. Flash 和 Pro 各完成一次真实项目任务
2. 项目长期记忆可召回，另一项目不能召回该项目历史
3. 全局用户偏好可跨项目召回
4. 阿里云、本地和纯 FTS5 三条检索路径均可完成任务
5. 超长消息被明确拒绝，Prompt 预算和 memory refs 可在 UI 查看
